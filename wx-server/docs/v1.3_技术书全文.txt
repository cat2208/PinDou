0. 阅读约定
所有价格单位为人民币元，精确到分。
所有"可配置"参数（豆子单价、手工单价、烫费、配件费、运费、包邮阈值、套餐价、时长阈值等）必
须存放在后端配置表，禁止硬编码。
所有涉及资金、计时、核销、状态流转的操作，必须由服务端校验，禁止仅依赖前端状态判断。
文中 SQL 为 MySQL 8.x 语法，时间统一使用 DATETIME，金额统一使用 DECIMAL(10,2)。
用户身份使用微信小程序 openid 作为主标识。
所有高危操作（定价变更、订单撤销/退款、库存调整、权限变更等）必须写入 audit_log，不可绕过。
多门店场景下，各门店的定价、库存、座位配置相互独立，通过 store_id 隔离。
[v1.2] IoT 座位指示灯为可选增值模块，后台全局开关控制启用/禁用；关闭时 IoT 模块完全不执行逻
辑，原有业务不受任何影响；硬件仅做状态展示，所有业务判断依然以数据库 seat 表为准，绝不依赖
硬件设备上报信号。
[v1.2] 所有新增配置项存入对应配置表，禁止硬编码；资金、锁、退款逻辑全部服务端校验。
[v1.3] 消息内容审核：用户发送的消息内容不做实时内容安全过滤（图片走微信内容安全检测 API），
但保留人工追溯能力——所有消息只写不改、不支持删除（逻辑软删除仅限违规处理场景）。
[v1.3] 积分操作原子性：积分增加/扣减必须与订单状态变更是同一事务（订单完成→积分入账），禁
止异步补偿（防止积分超发）。
[v1.3] 会员等级缓存：用户等级在 Redis 缓存，TTL 1 小时；积分变动触发等级重新计算，计算后刷新缓
存。
[v1.3] 质检照片即证据：质检照片上传后不可修改、不可删除，作为交付纠纷处理依据；水印自动叠加
时间戳与操作人。

    color_count <= color_threshold  -> labor_price_normal

    NORMAL  -> 0

    KEYCHAIN            -> accessory_keychain

    NO_HOLE_DOUBLE      -> accessory_no_hole_double
    FRAME               -> accessory_frame（装裱/配框）
运费 price_shipping     =
    shipping == false                                   -> 0
    total(豆+工+烫+配件) >= free_shipping_threshold      -> 0
    否则                                                -> shipping_fee
总价 total_price        = price_bean + price_labor + price_iron + 
price_accessory + price_shipping
定金 deposit            = total_price × deposit_ratio（默认 50%，可配置 
30%~50%）

14.3 业务规则
消息归属：定制订单消息归属于 assigned_staff_id （接单时指派）；到店订单归属于开台店员。
店员离职/换班不影响消息可读性（店长可查看全门店所有订单消息）。
消息类型：TEXT（纯文字）、IMAGE（图片+可选文字说明）、SYSTEM（系统自动消息，如"订单状态
变更为已接单"，不可回复）。
图片安全：用户上传的图片走 OSS 直传，后端回调时调用微信内容安全检测 API（msg_sec_check），
检测不通过则标记为违规，返回提示但不入消息列表。
已读机制：消息列表接口被调用时，自动将对方未读标记清零并更新 Redis 缓存角标。不需要单独调用
标记已读接口（但提供接口供主动刷新）。
消息不可删：用户不可删除自己发送的消息；仅店长可逻辑删除违规消息（is_deleted=1），操作写入
审计日志。删除后用户端显示"该消息已被管理员移除"。
有效期：订单状态为 CANCELLED 或 CONFIRMED 后 30 天内仍可查看消息；超过 30 天消息归档（逻辑
保留，不在列表展示，需后台手动查询）。
频率限制：同一用户 1 分钟内最多发送 10 条消息，防止刷屏；图片消息 1 分钟内最多 5 张。

档，作为交付证据。质检不通过可回退返工。
确认收货：订单标记 SHIPPED 后用户无法看到物流信息，也没有确认收货机制。如果用户声称未收到
货，系统没有签收证据。需要增加物流单号录入、用户确认收货、超期自动确认。

原 v1.2 状态流：
v1.3 新状态流：
QC_PENDING：熨烫完成，等待质检
QC_PASSED：质检通过，等待发货
DELIVERED：已发货（物流已揽收）
CONFIRMED：用户已确认收货 / 超期自动确认

16. 轻量会员体系
16.1 业务背景
拼豆手工店是典型的体验型消费门店，复购率是经营命脉。当前系统 user 表已有 member_level  和 
points  字段但无业务逻辑。本模块实现一期轻量会员体系：
消费积分：消费金额自动累积积分
会员等级：4 级体系，累计积分达到阈值自动升级
等级折扣：不同等级享受不同折扣比例
积分抵扣：下单时可用积分抵扣部分金额
生日福利：生日月双倍积分 + 免费熨烫
积分过期：12 个月未消费积分自动过期
16.2 积分规则
积分赚取：
触发时机：定制订单确认收货（CONFIRMED）后积分入账；到店订单结算（SETTLED）后积分入账；
配件/材料包订单支付完成（PAID）后积分入账。
计算公式：获得积分 = 实付金额 × points_per_yuan。实付金额 = 总价 - 积分抵扣 - 券抵扣（不含运
费）。
生日月双倍：当 birthday_double_points=1  且用户生日月与当前月一致时，获得积分 ×2。生日以 
user.birthday  字段为准。
积分过期：每笔积分入账时写入 expire_at （当前时间 + points_expire_months  个月）。定时任
务每日扫描 expire_at < NOW()  且 direction=1  的记录，生成 EXPIRE 流水扣减积分。
累计积分： cumulative_points  只增不减（过期不扣减累计值），用于等级判定。
原子性：积分入账与订单状态变更是同一数据库事务。订单取消/退款时，已入账积分通过 SPEND 流水
扣回（如积分不足则扣至0，记录负数流水标注"退款积分回收"）。

积分消费：
使用场景：定制订单下单、到店结算、配件/材料包下单时，用户可选择使用积分抵扣。
计算公式：抵扣金额 = 使用积分数 / points_to_yuan_rate （默认 100 积分 = 1 元）。
抵扣上限：积分抵扣金额 ≤ 订单应付金额 × points_deduct_max_ratio （默认 30%）。
扣减顺序：优先扣减即将过期的积分（FIFO 按 expire_at 排序）。
订单取消退回：订单取消时，已使用的积分原路退回（EARN 流水，expire_at 恢复原值）。退回的积分
如果已过期，则不退回。
并发控制：积分扣减使用 Redis 分布式锁 lock:points:user:{user_id} ，防止同时使用积分导致超
扣。
16.3 等级权益
等级计算规则：
自动升级：每次积分入账后，比较 cumulative_points  与 member_level_config  各等级阈值，取
满足条件的最高等级。升级写入 audit_log action=MEMBER_LEVEL_CHANGE 。
不自动降级：积分过期不降低 cumulative_points ，因此不影响等级。等级一旦升级永久有效（一
期策略，二期可调整为滚动窗口）。
折扣适用范围：等级折扣应用于订单总价（不含运费），在积分抵扣之前计算。顺序：总价 → 等级折
扣 → 积分抵扣 → 券抵扣 → 应付金额。
生日福利：双倍积分需 birthday_double_points=1  且 level >= 2；钻石会员生日月定制订单 
price_iron = 0 （系统自动减免，写备注"生日福利-免费熨烫"）。
等级配置可修改：PC 后台可修改各等级阈值和折扣率，修改写入审计日志。修改不影响已有等级的用
户。
